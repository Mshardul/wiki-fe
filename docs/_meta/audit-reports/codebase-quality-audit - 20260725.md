## Findings by concern

### Naming & terminology consistency

#### [MAJOR-CANDIDATE] CLAUDE.md's file map is missing 21 of 52 JS files (~40%)

- **Concern:** naming
- **Files:** `CLAUDE.md` FILE MAP section vs actual `js/` tree - missing entries for `js/app/complexity-compare.js`, `js/app/graph-engine.js`, `js/app/link-graph.js`, `js/app/section-map.js`, `js/app/sidecar-toc.js`, `js/content/depth-fold.js`, `js/content/freeze-frame.js`, `js/content/highlights.js`, `js/content/interview-mode.js`, `js/content/structure-viz.js`, `js/content/video-embed.js`, `js/icon-sprite.js`, `js/render/admin-view.js`, `js/render/index-graph.js`, `js/render/offline-view.js`, `js/search-features.js`, `js/toc-companion.js`, `js/storage/data-clear.js`, `js/storage/highlights.js`, `js/storage/interview-mode.js`, `js/storage/notes.js`
- **Observation:** CLAUDE.md's FILE MAP subtables for `js/app/`, `js/content/`, `js/render/`, `js/storage/` are the explicit routing mechanism the project instructs an AI agent to use instead of reading every file in a domain folder ("Never read every file in a domain folder ... the subtables below say exactly which file owns which behavior"). Cross-referencing every subtable entry against the actual files on disk shows 21 of 52 JS files - about 40% of the codebase, including entire features like admin, section-map/link-graph/index-graph (all three graph-view modules), interview mode, highlights/markers, notes, complexity-compare, and the toc-companion popup window - have no entry anywhere in the map. `js/toc-companion.js` and `js/search-features.js` (top-level, alongside `app.js`/`auth.js`/`api.js`) aren't even acknowledged as existing outside a domain folder.
- **Impact:** this is the audit's own method turned back on the source of truth: an agent following CLAUDE.md's routing table for, say, "admin page bug" or "interview mode bug" has no file-map entry to route to and must fall back to guessing or a full-tree search - exactly the inefficient behavior the file map exists to prevent. Any future task classified via the FILE MAP or TASK → FILE ROUTING tables risks silently missing the correct file for these 21 modules.
- **Fix direction:** regenerate the FILE MAP subtables against current `js/` tree contents; consider a lightweight CI check (or a periodic manual pass) that diffs `find js -name '*.js'` against files mentioned in CLAUDE.md so this doesn't silently drift again. Flagged as MAJOR-CANDIDATE rather than MAJOR outright since it's a docs/process gap, not a code defect, but it directly undermines a load-bearing project convention.

#### [MINOR] Two different ways to resolve a wiki from a content path in the same file

- **Concern:** naming
- **Files:** `js/render/related-articles.js:172-175` (`_wikiIdForPath`, uses `path.startsWith(`./content/${w.id}/`)`), `js/render/related-articles.js:247` (`renderBridges`, inlines `WIKIS.findIndex((w) => path.startsWith(`./content/${w.id}/`))` instead of calling `_wikiIdForPath`)

#### [MINOR] `load*` prefix used for synchronous reads, breaking the get/load convention the rest of the codebase follows

- **Concern:** naming
- **Files:** `js/state.js:162` (`loadStubPaths`, synchronous sessionStorage read), `js/state.js:184` (`loadShapeFingerprints`, synchronous sessionStorage read), vs `js/storage/bookmarks.js:13` (`getBookmarks`, synchronous localStorage read), `js/storage/recents.js:14` (`getRecents`), `js/storage/read-tracking.js:17` (`getReadSet`), `js/render/home-index.js:37` (`getPinnedWikis`)
- **Observation:** across the rest of the codebase, `get*` consistently names a synchronous read (localStorage/sessionStorage/memory) and `load*`/`fetch*` name an async operation, usually with caching (`loadSynonyms`, `loadStructures`, `loadAllSearchEntries`, `fetchText`, `fetchWikiIndex`). `state.js`'s `loadStubPaths()` and `loadShapeFingerprints()` break this: both are plain synchronous `sessionStorage.getItem` + `JSON.parse` reads with a try/catch fallback - functionally identical in shape to `getBookmarks`/`getRecents`/`getReadSet` elsewhere - yet named with the `load*` prefix the rest of the codebase reserves for async work.
- **Impact:** minor - a reader who has internalized "get = sync, load/fetch = async" from the rest of the codebase will misjudge these two functions' cost/blocking behavior from the name alone, or reach for `await` unnecessarily.
- **Fix direction:** rename to `getStubPaths`/`getShapeFingerprints` for consistency with the established convention (both are file-local within `state.js`, so the rename is low-blast-radius - just update the file's own call sites).

#### [POLISH] "Backdrop" vs "overlay" used interchangeably for the same click-outside-to-close scrim element

### Data types & structures

#### [MAJOR-CANDIDATE] `recents.js` skips the `sequencedMutation` race-guard that `bookmarks.js` and `read-tracking.js` both use for the identical write pattern

- **Concern:** design-patterns (cross-listed here because the root cause is a data-consistency guarantee, not just style)
- **Files:** `js/storage/recents.js:22-28` (`addToRecents`, calls `api.recents.add` directly, no `sequencedMutation`), vs `js/storage/bookmarks.js:26-37` (`saveBookmarks`, wraps every `api.bookmarks.add`/`.remove` in `sequencedMutation(key, ...)`), `js/storage/read-tracking.js:36-40,54-59` (`markRead`/`markUnread`, wrap `api.reads.add`/`.remove` in `sequencedMutation`)
- **Observation:** `state.js`'s `sequencedMutation` helper exists specifically (per its own doc comment) to prevent "a rapid double-fire ... from dispatch[ing] two requests for the same key out of order." Both `bookmarks.js` and `read-tracking.js` use it for their fire-and-forget backend writes. `recents.js`'s `addToRecents` fires `api.recents.add(entry.wikiId, entry.path)` (line 27) completely unguarded - and `addToRecents` fires on every single article navigation (`content-view.js:281`), including rapid back-to-back navigation (e.g. clicking through several links quickly, or a user double-tapping a link), which is exactly the "double-fire" scenario the helper was built for.
- **Impact:** under rapid navigation between articles, out-of-order `recents.add` network responses could leave the backend's recents list not matching actual visit order - a real, if minor, data-integrity bug, not just a style inconsistency.
- **Impact severity note:** flagged MAJOR-CANDIDATE rather than confirmed MAJOR - not behavior-verified (didn't reproduce the race in a browser), but the code shape is a clear, direct match to the exact case `sequencedMutation` was written to prevent.
- **Fix direction:** wrap `addToRecents`'s `api.recents.add` call in `sequencedMutation(`${entry.wikiId}|${entry.path}`, () => api.recents.add(...))` to match the other two modules.

#### [MINOR] Modal open/close-state convention split: `hidden` class vs `open` class

- **Concern:** data-structures

#### [MINOR] Three different state representations for "is this reading-mode toggle active"

- **Concern:** data-structures
- **Files:** `js/app/distraction-free.js:1` (`let _distractionFree = false` module-level boolean), `js/content/formatting.js:266-267,323` (`_focusMode`/`_studyMode` module-level booleans), `js/content/interview-mode.js:10` (`_interviewMode` module-level boolean), vs `js/content/formatting.js`'s own `ArticleFind._open` (line 394, a property on an exported object literal rather than a closed-over module variable), vs DOM-class-as-truth for mobile TOC (`js/app/mobile-panels.js:24-26`, `isMobileTocOpen()` reads `tocSidebar.classList.contains("mobile-open")` with no parallel JS variable at all)
- **Observation:** the app has at least three distinct conventions for tracking "is this full-article reading mode currently on": (1) a private module-scoped `let` boolean mirrored onto a DOM class (distraction-free, focus, study, interview - 4 instances of this same shape, at least consistent with each other), (2) a property on an exported singleton object (`ArticleFind._open`), (3) no JS-side variable at all - DOM class membership is the sole source of truth (mobile TOC, wiki-switcher/bookmarks-modal/link-graph/compare-picker's `hidden`-class modals, section-map's `open`-class overlay). None of these is wrong in isolation, but a reader moving between `js/app/` and `js/content/` has to re-learn which convention today's file uses before trusting `isXOpen()` to mean what it says.

- **Fix direction:** not a big rewrite - just worth a one-line convention note in CONVENTIONS.md ("boolean UI-mode state: module-level `let` + mirrored DOM class; don't invent a 4th shape") so the pattern stops being incidental.

### Design patterns & coupling

#### [MAJOR] Focus-trap reimplemented per-modal (4 independent copies, 4 modals with none)

- **Concern:** design-patterns
- **Files:** `js/auth.js:119-137` (`AuthModal._trapFocus`), `js/app/bookmarks-modal.js:16-18,56-74` (`_getFocusable`/`_focusTrapHandler`), `js/storage/settings-theme.js:366-382,426-431` (`Settings._focusTrapHandler`/`_getFocusable`), `js/search.js:556-575` (`_searchFocusTrapHandler`)
- **Observation:** four separate modules implement nearly identical Tab-cycle focus-trap logic (query focusable elements, compare `document.activeElement` to first/last, preventDefault+refocus) as four separate closures, each with a *different* focusable-element query: `auth.js` includes `a[href]` and filters by `offsetParent !== null`; `bookmarks-modal.js` only queries `button:not([disabled])` with no visibility filter at all; `settings-theme.js` queries `button:not([disabled]), input:not([disabled])` (no links) and filters by both `offsetParent !== null` AND `el.style.display !== "none"`; `search.js` doesn't query the DOM for focusables at all - it hardcodes `[gSearchInput, ...gSearchItems()]`, a fourth distinct strategy with no visibility filtering. `wiki-switcher.js`, `complexity-compare.js`, `link-graph.js`, `section-map.js` have NO focus trap at all (Tab can escape those modals to the page behind).
- **Impact:** any focus-trap bug fix (e.g. the visibility-check inconsistency itself) has to be found and applied in 4 places, each subtly different; the 4 modals without a trap are an accessibility gap that will only widen as more modals are added by copying whichever pattern is nearest.
- **Fix direction:** extract a shared `createFocusTrap(container, focusableSelector)` helper returning `{attach, detach}`; apply uniformly to every modal, including the 4 currently missing one.

#### [MINOR] Modal open-state query duplicated as `!el.classList.contains("hidden")` per module

- **Concern:** design-patterns
- **Files:** `js/app/bookmarks-modal.js:92-94` (`isBookmarksModalOpen`), `js/app/wiki-switcher.js` (no `isOpen` export at all - `app.js:464` reaches in directly via `document.getElementById("wiki-switcher-modal").classList.contains("hidden")`), `js/app/complexity-compare.js:135-137`, `js/app/link-graph.js:80-82`, `js/auth.js:139-141`

- **Impact:** `wiki-switcher` modal is one implementation detail change (e.g. renaming the element id, switching to a different closed-state signal) away from silently breaking the Escape-key chain in `app.js`, since that call site bypasses the module's own API.
- **Fix direction:** add `isWikiSwitcherOpen()` to `wiki-switcher.js` for symmetry; consider one shared `isModalOpen(id)` helper for the four identical implementations.

### Error handling consistency

#### [MAJOR] Unconditional `console.*` calls violate the explicit no-console rule

- **Concern:** error-handling
- **Files:** `js/state.js:31` (`console.warn` for duplicate WIKIS ids), `js/content/mermaid.js:21,341` (`console.warn("Mermaid render failed", err)` / `"Mermaid re-render failed"`), `js/render/home-index.js:904` (`console.warn("parseIndexMd: malformed row skipped:", ...)`)
- **Observation:** CLAUDE.md and CONVENTIONS.md both state "No `console.*` in committed code" as a non-negotiable, with the explicit remedy "surface it through the UI (toast/error state), not the console." These three call sites are unconditional `console.warn`s with no gating, unlike `api.js`'s `console.log` calls at lines 70/80 which are gated behind a `_DEBUG` flag (itself only a partial mitigation - CONVENTIONS.md separately bans "no file-local DEBUG flags" for logging). Every one of these is a genuine dev-facing failure (mermaid syntax error, malformed index row, duplicate wiki id) that currently has zero user-visible signal - the mermaid failure case even has a user-visible fallback right next to it (`errEl.textContent = "Diagram syntax error..."`) but still logs before applying it.
- **Impact:** these are exactly the kind of "silently swallowed with no user-visible signal" failures the audit brief calls out - in production (no devtools open) a malformed index row or a broken Mermaid diagram produces zero signal to the author who needs to fix it, and the rule violation itself will keep getting copied forward as a "precedent" if not caught.
- **Fix direction:** remove the `console.warn` calls; for `mermaid.js` the existing `errEl`/error-state UI already covers the user-facing side, so the console line is pure removal; for `home-index.js` and `state.js`, either surface via `showToast` (if actionable at runtime) or drop entirely since these are build/content-authoring errors, not runtime user errors. Revisit whether `api.js`'s `_DEBUG`-gated `console.log` should also go through a different debug channel (e.g. the existing `?debug` overlay) instead of `console`.

#### Confirmed clean: `ApiError` discrimination is consistent everywhere it matters

Every catch block handling a real backend call (`auth.js`'s login/register/verify/forgot/reset flows, `admin-view.js`'s user list/role/status calls) consistently uses `e instanceof ApiError ? e.message : <generic fallback>`, and `auth.js` additionally switches on `e.code`/`e.status` per CONVENTIONS.md's contract ("switch on the machine code, never on the human message text") for the two cases that need it (403 → unverified account, `INVALID_TOKEN` → reset-link handling). The two call sites that print `err.message` unguarded (`home-index.js:167`, `content-view.js:497`) are catching `nav-utils.js`'s `fetchText`, which throws plain `Error` for content/markdown fetch failures (a different, non-backend domain by design) - not a violation of the `ApiError` contract. Not a finding; the pattern holds up under a full-tree grep of every `instanceof ApiError` and `.message` reference.
