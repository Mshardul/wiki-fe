# Auth UX Audit

Generated by auth UX audit agent. FE-only — see wiki-be's companion audit for backend findings.

**Methodology:** Phase 1 was a static read of `js/auth.js`, `js/api.js`, `css/components/auth.css`, `js/state.js` (`state.session`), `js/render/toast.js`, `js/storage/settings-theme.js` (`Sync` / multi-tab listener), `js/storage/bookmarks.js` + `recents.js` + `completions.js` (anon-data carryover), `index.html` auth/migrate markup, and the password/error contract in `docs/_meta/auth.md`. Phase 2 was a live browser pass against `http://localhost:8000` (FE) + `http://localhost:8001` (local wiki-be). Playwright MCP could not launch (`Chromium distribution 'chrome' is not found` — known MCP channel vs bundled Chromium). Live verification used the same Chromium bundle as e2e (`~/Library/Caches/ms-playwright/chromium-1237`, headless). Findings that needed runtime are marked `[LIVE]`. Code-only findings are `[CODE-CONFIRMED]`.

**Environment notes:** Local BE had no `RESEND_API_KEY` (dev skip-send). Happy-path verify/reset email links were `[UNTESTABLE]`; junk `?mode=verify|reset&token=…` URLs were driven instead. One account was marked `email_verified=1` / `is_active=0` via sqlite only to reach login-after-verify and deactivated-login — not a FE code path.

**Prior run (2026-07-13):** Phase 2 never ran. Several Jul 13 items are now closed (confirm-password, panel-swap checklist desync, submit loading state). This pass does not re-log those.

### Register form

#### [MAJOR] FE password checklist accepts a space as the special character; BE rejects it

- **Flow step:** Register — password validation
- **File:** `js/auth.js:29-32` (`PW_RULES` special test `/[^A-Za-z0-9]/`); live UI register panel
- **Repro:** `[LIVE]` Type `AuditPass1 xx` (12+ chars, upper, lower, digit, space as the only non-alnum). Special-character checklist item turns `.ok`. Confirm the same value and submit. Error: "Password does not meet the requirements." Panel stays on register.
- **Impact:** The live checklist and the disabled-until-green submit gate both lie. `docs/_meta/auth.md` still says special is "anything outside `[A-Za-z0-9]`" (which includes space). BE (WIKI-BE-36) excludes whitespace. User sees a green checklist, then a generic reject.
- **Fix direction:** Tighten the FE special test to match BE (exclude whitespace, ideally the same allowed set as the hint `! @ # $ % ^ & * ? - _`). Update `auth.md` so the two implementations and the doc stay one rule.

#### [MINOR] Password-manager autofill that does not fire `input` leaves the checklist and submit gate stale

- **Flow step:** Register — autofill
- **File:** `js/auth.js:561-572` (checklist only on `input`)
- **Repro:** `[LIVE]` Set `#auth-reg-password.value` without dispatching `input` (password-manager autofill often does this). Checklist stays all "not met", submit stays disabled, even though the field holds a fully valid password. Dispatching `input` updates the checklist immediately.
- **Impact:** Autofill can look like "my password is invalid" until the user types one extra character. Confirm field still has to match, so this is incomplete even after the event.
- **Fix direction:** Also listen to `change`/`animationstart` (Chrome autofill) or re-sync checklist on submit-button mousedown / form `submit` before the valid check.

### Resend verification

#### [MAJOR] Non-network resend failures still toast "Verification email sent"

- **Flow step:** Resend verification
- **File:** `js/auth.js:441-455` (comment still says "generic 200 either way (anti-enumeration)")
- **Repro:** `[CODE-CONFIRMED]` Any `api.auth.resend` rejection that is not `NETWORK`/`TIMEOUT` takes the else branch and shows "Verification email sent". After WIKI-BE-35 the API returns honest errors (e.g. already-verified, unknown user, rate limit). `[LIVE]` cooldown itself works: second click while `data-cooldown-active` cannot fire (Playwright timeout on disabled button).
- **Impact:** User can be told the email went out when it did not. Comment and UX still assume the old anti-enumeration contract.
- **Fix direction:** Map `e.code` to the same honest messages used on register/forgot; only show the success toast on 2xx. Drop the stale anti-enumeration comment.

### Login

#### [CRITICAL] "Keep them" on anon→login wipes local completions

- **Flow step:** Anon → account migration / Login
- **File:** `js/auth.js:50-101` (`_hasLocalCompletions` feeds `_hasLocalData`; `maybeMigrate` import payload is bookmarks+recents only); `js/storage/settings-theme.js:908-933` (`Sync.pullAll` overwrites `wiki-completed-*` from the server list)
- **Repro:** `[LIVE]` As anon, `localStorage['wiki-completed-dsa'] = ["algorithms/bfs.md"]`, no bookmarks/recents. Log in. Migrate modal appears ("You have unsaved items…"). Escape and backdrop click do nothing. Click **Keep them**. After login, `wiki-completed-dsa` is gone (`null`). Toast: "Logged in".
- **Impact:** The modal exists to preserve signed-out progress. Completions are the only progress primitive left after WIKI-593. Choosing Keep imports bookmarks/recents (empty) then `pullAll()` replaces completions with the server set (empty for a new account). Discard would also clear them — there is no keep path that works.
- **Fix direction:** Include completions in the `importAll` payload (needs BE `/sync/import` to accept them — today FE `api.importAll` posts whatever the caller sends; if import rejects completions, add a completions bulk upsert and call it before `pullAll`). Do not call `pullAll()` until local completions have been written server-side. Same gap for notes/highlights is called out under migration as a separate, lower-severity miss.

#### [MAJOR] Deactivated account is shown as "Account not verified"

- **Flow step:** Login — 403 handling
- **File:** `js/auth.js:393-402` (`e.status === 403` → verify panel, ignores `e.code`)
- **Repro:** `[LIVE]` Verified user, `is_active=0`. Login with correct password. Modal swaps to `#auth-panel-verify`, title "Account not verified", copy about resending the verification email. Login error element stays empty.
- **Impact:** Wrong diagnosis and a useless resend path. A deactivated user cannot verify their way back in. Any other 403 (including `ACCOUNT_DEACTIVATED`) is conflated with unverified.
- **Fix direction:** Branch on `e.code` (`ACCOUNT_DEACTIVATED` vs unverified/forbidden). Show a dedicated error on the login panel; do not offer resend.

#### [MINOR] Login password field has no show/hide toggle

- **Flow step:** Login form
- **File:** `index.html` login panel vs register/reset (`#auth-reg-pw-toggle`, `#auth-reset-pw-toggle`)
- **Repro:** `[LIVE]` Login password is a bare `<input type="password">`. Register and reset both have eye toggles.
- **Impact:** Long policy-compliant passwords are hard to check on login; register already solved this.
- **Fix direction:** Reuse `_wirePasswordToggle` on `#auth-login-password`.

### Forgot / reset password

#### [MAJOR] Forgot-password copy still pretends anti-enumeration; live API returns "User not found."

- **Flow step:** Forgot password
- **File:** `index.html` `#auth-forgot-sent` ("If that account exists, a reset link is on its way."); `js/auth.js:483-492` shows `_authErrorMessage` (raw `e.message`) on any error
- **Repro:** `[LIVE]` Unknown email → error "User not found.", success copy stays hidden. Same string then appeared for the just-registered (still-unverified at that moment) address. Success and error can both show at once (see next finding).
- **Impact:** Honest 404 leaks account existence (product-accepted on the BE after WIKI-BE-35) but the leftover success copy still claims the opposite. Raw "User not found." is not actionable ("check the address" / "register first").
- **Fix direction:** On 2xx, show sent copy and clear the error. On `USER_NOT_FOUND` (and friends), hide sent copy and use a FE-mapped sentence. Do not keep both visible. Align the sent sentence with whatever the API actually does.

#### [MAJOR] Forgot success does not clear a prior error, so error + "sent" render together

- **Flow step:** Forgot password — retry
- **File:** `js/auth.js:483-486` (success only unhides `#auth-forgot-sent`; `_clearErrors` is not called)
- **Repro:** `[LIVE]` Submit unknown email (error visible) then submit again. `err_hidden=False` and `sent_hidden=False` together.
- **Impact:** Contradictory messages on the same panel.
- **Fix direction:** Call `_clearErrors()` at the start of `forgotPassword`, or hide the error element on the success path.

#### [OK] Junk reset token

`[LIVE]` `/?mode=reset&token=deadbeef` opens the reset panel, strips the query, submit with a valid new password shows the dedicated expired-link message.

#### [UNTESTABLE] Happy-path reset (real token) and "old password stops working"

No inbox; tokens are hashed at rest so they cannot be lifted from sqlite.

#### [MINOR] Reset-password success has no toast (login does)

- **Flow step:** Reset password
- **File:** `js/auth.js:505-514` vs `login` which toasts "Logged in"
- **Repro:** `[CODE-CONFIRMED]` Reset sets the session, closes the modal, `pullAll`, broadcasts — no `showToast`.
- **Impact:** Easy to miss that you are now logged in.
- **Fix direction:** Same success toast as login, or "Password updated".

### Anon → account migration

(Critical completions wipe is under Login.)

#### [MAJOR] Migrate modal is not in the modal registry: no Escape, no backdrop dismiss, no focus trap

- **Flow step:** Anon → account migration
- **File:** `js/auth.js:58-80`; `index.html` `#migrate-modal`; no `registerModal` / no `.migrate-backdrop` click listener
- **Repro:** `[LIVE]` Modal open: Escape leaves it visible; clicking `.migrate-backdrop` leaves it visible. Only Keep/Discard resolve the promise. Auth modal is already closed, so the Escape chain does not help.
- **Impact:** Keyboard-only and mis-tap users cannot dismiss. A pending promise holds the login flow until a button is clicked. Contrast: auth modal has trap, backdrop click, and registry Escape.
- **Fix direction:** Register it like other modals, trap focus in `.migrate-dialog`, backdrop + Escape = Discard (or Keep — pick one and say it in copy), restore focus after.

#### [MINOR] Notes and highlights never participate in the migrate prompt

- **Flow step:** Anon → account migration
- **File:** `js/auth.js:54-56` (`_hasLocalData` is bookmarks || recents || completions only)
- **Repro:** `[CODE-CONFIRMED]` Notes/highlights keys can exist; they do not open the modal. Keep does not upload them; Discard via `Sync.clearUserDataCache()` would wipe them if the modal had opened for another reason.
- **Impact:** Copy says "unsaved items" but the set is not the full personal layer. Notes stay local-only until WIKI-590 — surprising only if the user expected Keep to mean "everything on this device".
- **Fix direction:** Either mention completions/bookmarks/recents explicitly in the copy, or include notes/highlights in the prompt (even if Keep only preserves them locally until sync exists).
