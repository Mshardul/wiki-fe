### zoom-lightbox.js

### [MINOR] Pinch-zoom-then-release can trigger an accidental swipe-dismiss using stale `startX`/`startY` from an unrelated earlier single-finger gesture
- **Type:** isolation
- **Component(s):** `js/content/zoom-lightbox.js`
- **Parameter:** isolation correctness
- **File:** `js/content/zoom-lightbox.js:70-143` (`bindZoomGestures` touchstart/touchmove/touchend handlers)
- **Repro:** Open the zoom overlay, single-finger-tap-drag briefly (sets `startX`/`startY` to that gesture's coordinates, `touches.length === 1` branch), lift off, then start a two-finger pinch gesture (`touches.length === 2` branch — `startX`/`startY` are NOT updated in this branch, only `startDist`/`startScale`). Pinch back down to scale ≈1 and lift one finger so `changedTouches.length === 1` fires in `touchend` while `scale <= 1`. The swipe-dismiss check (`const dy = e.changedTouches[0].clientY - startY;`) computes `dy`/`dx` against the **stale** `startX`/`startY` left over from the earlier single-finger gesture, not from where the pinch actually ended.
- **Impact:** A pinch-to-zoom-out-then-release gesture can spuriously close the zoom overlay (`closeZoomOverlay()`) if the stale coordinate delta happens to exceed the 80px downward-swipe threshold, even though the user made no downward swipe motion at all in the current gesture. Requires a specific two-gesture sequence, so likelihood is real-but-uncommon on touch devices.
- **Fix direction:** reset/clear `startX`/`startY` (or set a `pinchOccurred` flag) whenever a 2-finger touch begins, and skip the swipe-dismiss check if the immediately-preceding gesture was a pinch rather than a single-finger drag.

### mermaid.js

### [MAJOR] Mermaid rendering loop has no render-generation guard while awaiting — stale-navigation mermaid.render() calls can run against the wrong/detached body
- **Type:** interaction
- **Component(s):** `js/content/mermaid.js` (`renderMermaidDiagrams`) + `js/render/content-view.js`
- **Parameter:** state/lifecycle
- **File:** `js/render/content-view.js:333` (`await renderMermaidDiagrams(body);` — no gen check immediately before/after; next check is line 353) and `js/content/mermaid.js:4-28` (the `for...of` loop with `await mermaid.render(...)` per diagram, no generation/cancellation token accepted)
- **Repro:** Navigate to an article with 2+ mermaid diagrams (rendering is not instant — `mermaid.render()` is async per-diagram), then immediately navigate to a second article before the first article's mermaid loop finishes. `renderContent` for the second navigation runs `body.innerHTML = buildLoadingSkeleton(...)` (line 248) then later its own content into the *same* `#markdown-body` node. The first render's `renderMermaidDiagrams` loop is still executing, holding `pre` element references captured from a `querySelectorAll` snapshot taken before the second render wiped the DOM; those `pre` nodes are now detached (removed from `body` by the second render's innerHTML replacement), so `pre.replaceWith(wrapper)` in the first loop's iteration becomes a no-op against a detached node — but `mermaid.render()` calls, `Date.now()`-based ID generation, and console output still execute wastefully, and if IDs collide with the second render's own mermaid IDs (both use `Date.now()`-seeded ids in the same event-loop tick range) internal mermaid DOM/state could still cross-contaminate.
- **Impact:** Wasted rendering work is the benign case; the concerning case is any timing window where the first-render's mermaid output briefly appears in the new article's DOM before being caught, or an ID collision inside mermaid's own internal render zone corrupts the second article's diagram output silently. No visible error to the user either way. Same underlying pattern as the already-flagged `related-articles.js` render-generation gap, but here on the highest-traffic path (every article navigation touches mermaid, or at least calls the function and no-ops).
- **Fix direction:** thread the `gen`/`_renderGen` token into `renderMermaidDiagrams` (accept it as a param or check `gen !== _renderGen` between each `await mermaid.render()` call inside the `for` loop) and bail early once stale, mirroring the guard already used for `fetchText` and the callout/collapsible step.

### [MINOR] Mermaid step-through label/rail state visually desyncs from the diagram after a theme-change re-render
- **Type:** isolation
- **Component(s):** `js/content/mermaid.js`
- **Parameter:** state/lifecycle
- **File:** `js/content/mermaid.js:315-348` (`rerenderMermaidDiagrams`)
- **Repro:** On an article with a step-through mermaid diagram, click through to step 3 of 5 (rail shows "Step 3/5", nodes highlighted `step-active`), then change the theme (triggers `rerenderMermaidDiagrams` via `wiki:themechange`). The function re-renders `wrapper.innerHTML = svg` (a fresh SVG with no `step-active` classes anywhere) and re-appends the existing `rail`/`playBtn` DOM nodes (which still show "Step 3/5" text and `data-step-index="2"`), but never re-calls `_applyMermaidStep` to re-apply the highlight to the new SVG's nodes.
- **Impact:** After any theme change mid-walkthrough, the step rail keeps showing the correct step number/caption text but the diagram itself silently loses all node highlighting — looks like step-through "reset" visually without the label agreeing, until the user clicks next/prev (which re-applies via `goToStep`'s fresh `querySelector`).
- **Fix direction:** after re-render, if `existingRail` is present and not hidden, re-derive `stepIndex` from `existingRail.dataset.stepIndex` and call `_applyMermaidStep` again against the new SVG before returning.

### tables.js

### [MINOR] Table column sort uses a non-transitive comparator for mixed numeric/non-numeric columns
- **Type:** isolation
- **Component(s):** `js/content/tables.js`
- **Parameter:** isolation correctness
- **File:** `js/content/tables.js:121-131` (`addTableSort`'s `doSort`)
- **Repro:** Sort a table column containing a mix of numeric-looking cells (e.g. `"5"`, `"3"`) and non-numeric cells (e.g. `"N/A"`, `"—"`). The comparator only takes the numeric fast path when **both** compared cells parse as numbers (`!Number.isNaN(aNum) && !Number.isNaN(bNum)`); any pairwise comparison involving one numeric and one non-numeric cell falls back to `localeCompare`, which orders by string value, not by any "numbers before/after text" policy. Across 3+ rows this produces a comparator that is not consistent/transitive.
- **Impact:** Sort order for columns with any non-numeric cell (common for complexity tables using "N/A", "-", or footnote markers) can look scrambled or inconsistent between clicks, especially in browsers/engines where `Array.prototype.sort`'s handling of non-transitive comparators varies. Low-severity since it only affects visual ordering, not data integrity.
- **Fix direction:** decide and apply one consistent rule for cells that don't parse as numbers (e.g. always sort them after all numeric cells) instead of falling back to raw string comparison only for mixed pairs.

### toc.js

### [MAJOR] TOC chevron collapse and in-content heading collapse button persist to two different localStorage keys for the same visual section — state drifts apart across a reload
- **Type:** isolation
- **Component(s):** `js/content/toc.js` + `js/storage/scroll-collapse.js`
- **Parameter:** persistence / state-lifecycle
- **File:** `js/content/toc.js:42` (`collapseKey = wiki-toc-h2-${wikiId}-${h.id}`, used only by the TOC chevron's `toggleCollapse(collapseKey, group)` at line 54) vs `js/content/toc.js:170` (`key = wiki-heading-collapsed-${wikiId}-${slugBase}-${h2.id}`, used only by the in-content collapse button's `toggleCollapse(key, h2, nowCollapsed)` at line 194)
- **Repro:** On an article, collapse an H2 section using only the TOC sidebar chevron (never the in-content collapse button next to the heading itself). `_syncContentH2` immediately mirrors the collapsed visual state onto the in-content heading in the same session, so both look collapsed. Reload the page (or navigate away and back). `buildTOC` restores the TOC chevron's collapsed state from `wiki-toc-h2-*` (correctly collapsed, since that's the key that was written), but `injectHeadingCollapseToggles` independently restores the in-content heading's collapsed state from `wiki-heading-collapsed-*` (never written, so it restores expanded) — the two now visually disagree on reload even though the user only ever performed one collapse action that looked, at the time, like it affected "the section" as a single concept.
- **Impact:** A real, easily reproduced persistence bug — any user who reads long articles and uses the TOC to collapse sections they've finished (a documented core feature: "TOC build, sticky section header, per-heading collapse" per CLAUDE.md) will find their collapse state silently half-reverted on every reload, depending on which control they happened to use. Same issue in reverse if the in-content button is used instead.
- **Fix direction:** use a single shared key per H2 section (e.g. always the `wiki-heading-collapsed-*` format) for both the TOC chevron and the in-content button, so one write is read by both restore paths.

### formatting.js

### [MINOR] `_substituteLatex` regex can mis-tokenize multi-char control sequences
- **Type:** isolation
- **Component(s):** `js/content/formatting.js`
- **Parameter:** isolation correctness
- **File:** `js/content/formatting.js:181-185`
- **Repro:** A LaTeX string containing a bare command letter as part of a longer alphanumeric control word not caught by the `(?<!\\)` lookbehind in unexpected ways — e.g. `\sin` — the regex only excludes a character immediately preceded by a single backslash char, so `\sin(x)` — `s`,`i`,`n` all directly follow `\` or a preceding matched letter and are excluded correctly for the first letter after `\` only (`s` is preceded by `\`, excluded) but `i` and `n` are preceded by plain letters, not `\`, so they get treated as free variables and wrongly wrapped in `\text{...}` if they appear in VAR_MAP (`n` is in VAR_MAP → "size"). Example: `\sin(n)` renders fine but a bare `\sin` immediately followed by variable `n` with no separator, e.g. `\sinn`, would corrupt `n` mid-word — edge case, but more realistically any LaTeX macro whose name ends in a VAR_MAP key letter immediately followed by a substitutable variable produces corruption without whitespace between them.
- **Impact:** Formula toggle can silently produce mathematically wrong substituted LaTeX for formulas using multi-letter macros adjacent to single-letter variables. Low likelihood in this wiki's actual content but a genuine correctness gap in the substitution logic.
- **Fix direction:** exclude characters that are part of a `\command` word (i.e. also check that the preceding character isn't a letter following a backslash-prefixed run), not just the immediately-preceding character.

### search.js

### [MAJOR] Retrying a failed search-index load duplicates every entry into the shared search cache
- **Type:** isolation
- **Component(s):** `js/search.js` + `js/state.js`
- **Parameter:** failure-path / state-lifecycle
- **File:** `js/search.js:428-472` (`loadAllSearchEntries`, `retryGlobalSearch`) and `js/state.js:137` (`const allSearchCache = { loaded: false, loading: false, entries: [] };`)
- **Repro:** Trigger `loadAllSearchEntries()` to fail for at least one wiki but partially succeed for at least one other (`anySucceeded === true` so the loading UI does NOT show the full-failure retry screen) — or more directly, get the full-failure retry screen (all wikis fail) and click the "Retry" button (`retryGlobalSearch()`). `retryGlobalSearch` sets `allSearchCache.loaded = false` and calls `loadAllSearchEntries()` again, which re-populates `allSearchCache.entries` via `.push(entry)` for every wiki's index — but `entries` is never cleared/reset anywhere (`allSearchCache.entries = []` never happens after the initial module-load default in `state.js:137`). Any entries already pushed from the first (failed-then-partially-succeeded, or fully-retried) attempt remain in the array, and the retry's successful entries are appended on top.
- **Impact:** After any retry (or any scenario where `loadAllSearchEntries` runs more than once with `allSearchCache.loaded` reset to `false` in between — e.g. a flaky network on first load), every search performed for the rest of the session returns duplicate result rows for every article from wikis that were loaded more than once — visually cluttered, and `gSearchCount`'s result count is inflated/wrong. `allSearchCache` is a module-level singleton that persists for the whole page lifetime (no reset on navigation), so this compounds if retry is hit multiple times in one session.
- **Fix direction:** in `retryGlobalSearch` (or at the top of `loadAllSearchEntries`), reset `allSearchCache.entries = []` before re-populating, alongside the existing `loaded`/`loading` flag resets.

### [MINOR] Command-mode verb-arg preview can go stale if the underlying data changes between preview and Enter
- **Type:** isolation
- **Component(s):** `js/search.js`
- **Parameter:** state/lifecycle
- **File:** `js/search.js:340-370` (`_resolvedArgRun` / `applyCommandFilter`'s verb-mode branch) and `414-426` (`runSearchCommand`)

### auth.js

### [MAJOR] Cross-tab session-sync listener updates login UI without pulling server data — other tabs show "logged in" with stale/anonymous local bookmarks, reads, and recents
- **Type:** isolation
- **Component(s):** `js/auth.js`
- **Parameter:** state/lifecycle (multi-tab) / persistence
- **File:** `js/auth.js:494-508` (`window.addEventListener("storage", ...)` cross-tab session sync handler)
- **Repro:** Open the wiki in two tabs while logged out (or as two different users on the same browser profile, sequentially). In tab A, log in. `Auth.login()` correctly calls `await Sync.pullAll()` (line 268) before broadcasting via `_broadcastSessionChange()`. Tab B's `storage` listener fires, re-probes `GET /auth/me`, sets `state.session = { user, status: "in" }`, and calls `Auth.refreshButtons()` + dispatches `wiki:session-changed` — but never calls `Sync.pullAll()`. Tab B's topbar now shows "Logout" (and reveals the admin nav if applicable) as if fully logged in, but `localStorage[wiki-bookmarks]`, `wiki-read-*`, and `wiki-recents` in tab B still hold whatever was there before (anonymous/stale/a previous user's data) — none of it has been reconciled with the server.
- **Impact:** A real, reachable multi-tab desync: tab B's UI asserts "you are logged in as this user" while every localStorage-backed feature (bookmarks list, read state, recents) silently continues showing pre-login local data until the user manually reloads tab B. The reverse case is worse: on cross-tab **logout**, the same listener's `.catch()` branch sets `status: "out"` and refreshes buttons, but never calls `Sync.clearUserDataCache()` (which the real `Auth.logout()` does call) — so tab B flips its UI to "Login" while leaving the just-logged-out user's synced bookmarks/recents/read-state sitting in localStorage, now visible to anyone who continues using that browser as if it were anonymous local data.
- **Fix direction:** call `await Sync.pullAll()` after confirming `status: "in"` in the storage-sync success branch, and call `Sync.clearUserDataCache()` in the `.catch()` (logged-out) branch, mirroring exactly what `Auth.login()`/`Auth.logout()` already do for the initiating tab.

### [MINOR] Auth boot re-probe on cross-tab session-sync can race a user's in-flight local action
- **Type:** isolation
- **Component(s):** `js/auth.js`
- **Parameter:** state/lifecycle (multi-tab)
- **File:** `js/auth.js:494-508` (the `SESSION_SYNC_KEY` storage listener)
- **Repro:** Log in in tab A (fires `_broadcastSessionChange()`, bumping `SESSION_SYNC_KEY`). Tab B, previously anonymous, receives the storage event and calls `api.auth.me()` to re-probe, then on resolve calls `Auth.refreshButtons()` and dispatches `wiki:session-changed`, which (per `app.js:116-118`) triggers `route(location.hash.slice(1))` - i.e. tab B silently re-renders its current view out from under the user. - **Impact:** Real but narrow - only triggered by a second tab detecting a login/logout event elsewhere. Re-rendering the current route on session change is likely intentional (to pick up per-user bookmarks/reads for the newly-identified session), but it comes with no preservation of scroll position, open modals, or in-progress input, which could feel like the page "jumped" unexpectedly to a user who didn't initiate the login in that tab.

### bookmarks-modal.js

### [MINOR] `openBookmarksModal` doesn't guard against being called while already open, leaking a Tab-focus-trap keydown listener per extra open
- **Type:** isolation
- **Component(s):** `js/app/bookmarks-modal.js` + `js/app.js`
- **Parameter:** resource lifecycle / state-lifecycle
- **File:** `js/app/bookmarks-modal.js:46-75` (`openBookmarksModal`) — compare to `js/search.js:574` which explicitly does `if (_searchFocusTrapHandler) gSearchModal.removeEventListener(...)` before re-adding, a guard `bookmarks-modal.js` lacks
- **Repro:** `openBookmarksModal()` is reachable from two independent triggers with no shared open-check: `data-action="bookmarks-modal-open"` click delegation (`js/app.js:225`) and the `⌘B`/`Ctrl+B` global keyboard shortcut (`js/app.js:435-438`). If it's called a second time before an intervening `closeBookmarksModal()` (e.g. a fast double keypress, or the click-delegated button and the shortcut firing close together), `_focusTrapHandler` is overwritten with a new closure and `modal.addEventListener("keydown", _focusTrapHandler)` attaches a second listener — the first listener reference is now unreachable (overwritten in the module-level variable) so `closeBookmarksModal`'s single `removeEventListener(_focusTrapHandler)` can only ever remove the most recent one, permanently leaking the earlier listener(s).

- **Type:** interaction

- **Fix direction:** either (a) await `Auth.init()` before allowing interactive writes / block relevant buttons until `state.session.status !== "loading"`, or (b) queue writes made during "loading" and replay them against the API once session status resolves to "in", or (c) have `Sync.pullAll()` merge rather than blindly overwrite for any localStorage key touched after boot started.
