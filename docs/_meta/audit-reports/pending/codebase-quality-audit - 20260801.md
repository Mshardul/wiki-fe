### Naming & terminology consistency

#### [MINOR] Two different ways to resolve a wiki from a content path in the same file

- **Concern:** naming
- **Files:** `js/render/related-articles.js:174-175` (`_wikiIdForPath` via `WIKIS.find` + `path.startsWith`), `js/render/related-articles.js:251-253` (`WIKIS.findIndex` + same `startsWith` pattern, then index into a parallel array)
- **Observation:** prior audit already flagged this; both helpers still coexist in `related-articles.js`. One returns a wiki id string; the other returns `{ wikiId, wikiTitle, card }` via findIndex. Same path→wiki predicate, two call shapes.
- **Impact:** next cross-wiki feature in this file will copy whichever neighbor it sees first; the two can drift (e.g. one updated for a path-prefix change, the other not).
- **Fix direction:** make `_wikiIdForPath` (or a shared `wikiForPath` in `nav-utils.js`/`state.js`) the single primitive; have the bridges path call it instead of re-finding by index.

#### [MINOR] `load*` prefix still used for synchronous reads

- **Concern:** naming
- **Files:** `js/state.js:163` (`loadStubPaths`), `js/state.js:185` (`loadShapeFingerprints`), vs async `loadSynonyms` (`js/state.js:141`), `loadAllSearchEntries` (`js/search.js:434`), `loadStructures` (`js/app/complexity-compare.js:14`), `loadIconSprite` (`js/icon-sprite.js:1`), `loadAllFonts` (`js/storage/settings-theme.js:63`)
- **Observation:** most of the tree uses `get*` for sync local/storage reads (`getBookmarks`, `getRecents`, `getReadSet`, `getSettings`, `getCachedHtml`) and `load*` for async/network-ish work — but `loadStubPaths` / `loadShapeFingerprints` remain sync cache fills named like loaders.
- **Impact:** readers cannot trust `load*` ⇒ awaitable; encourages copy-paste of the wrong shape when adding the next cache.
- **Fix direction:** rename sync fillers to `get*`/`ensure*` (e.g. `ensureStubPaths`) and keep `load*` for async only; document the one-liner in CONVENTIONS if not already crystal-clear.

#### [POLISH] "Backdrop" vs "overlay" still interchangeable for click-outside scrims

- **Concern:** naming
- **Files:** `js/app.js:421-423` (`prefs-backdrop`, `auth-backdrop`), `js/app/bookmarks-modal.js:100` (`bookmarks-modal-backdrop`), vs `js/app/wiki-switcher.js:7` (`wiki-switcher-overlay`), `js/app/complexity-compare.js:151` (`compare-overlay`), `js/app/link-graph.js:76` (`link-graph-overlay`), `js/app/section-map.js:49` (`section-map-overlay`), `js/app/mobile-panels.js:13` (`toc-mobile-overlay`)
- **Observation:** same UX role (dimmed click-outside-to-close layer) still splits on element-id vocabulary: registry modals tend toward `*-backdrop`, canvas/drawer layers toward `*-overlay`. Zoom even nests both (`zoom-overlay` + `zoom-overlay-backdrop` in `js/content/zoom-lightbox.js:6-11`).
- **Impact:** search/grep for “how do I wire a new modal scrim?” returns two precedents; low runtime risk.
- **Fix direction:** pick one term in CONVENTIONS (“scrim id suffix: `-backdrop` for registry modals, `-overlay` for full-viewport layers”) or gradually rename; no behavior change required.

#### [MINOR] Modal open/close-state convention split: `hidden` class vs `open` class

- **Concern:** data-structures
- **Files:** `hidden`-removal as open: `js/auth.js:146-147`, `js/search.js:813-814`, `js/app/bookmarks-modal.js:77-78`, `js/app/wiki-switcher.js:50-51`, `js/app/complexity-compare.js:145-146`, `js/app/link-graph.js:72-73`, `js/storage/settings-theme.js:396-397`; `open`-addition as open: `js/app/section-map.js:85-86`, `js/content/zoom-lightbox.js` (via `classList.contains("open")` call sites in `js/app.js:487`, `js/app/mobile-panels.js:49`), mobile TOC (`js/app/mobile-panels.js:26` / `mobile-open`)
- **Observation:** registry modals consistently invert `hidden`; overlays/drawers consistently assert `open` / `mobile-open`. Internally each family is consistent, but Escape/close-stack code in `js/app.js` and `js/app/mobile-panels.js` must mix both predicates.
- **Impact:** next overlay copied from a modal (or vice versa) will wire the wrong class and ship a “close does nothing” bug.
- **Fix direction:** keep both DOM conventions if CSS needs them, but route all `isOpen` checks through `registerModal` / shared helpers so call sites never hand-roll `contains("hidden")` vs `contains("open")`.

### Design patterns & coupling

#### [MINOR] Four near-identical `related-grid` card-rendering templates in one file

- **Concern:** design-patterns
- **Files:** `js/render/related-articles.js:111-122` (recommended), `:153-164` (auto-suggest), `:198-211` (backlinks), `:265-279` (bridges)
- **Observation:** still four template-literal blocks building `related-grid` / `related-card` / title / arrow; bridges variant adds `bridge-card` + wiki subtitle and has already drifted.
- **Impact:** structural card changes require four edits; drift already visible on the bridges branch.
- **Fix direction:** local `_renderCardGrid(label, items, cardHtmlFn)` helper used by all four sites.

#### [MINOR] `extractRecommendedLinks` still walks `heading.nextElementSibling` despite `section-wrap`

- **Concern:** design-patterns
- **Files:** `js/content/section-wrap.js:9-16` (`_collectUntil` — documented as the replacement for repeated sibling walks), `js/render/related-articles.js:82-92` (still `while (node && node.tagName !== "H2")` + `nextElementSibling`, then `el.remove()`)
- **Observation:** section-wrap centralizes “everything under this heading,” but recommended-links extraction still re-derives H2 boundaries with a sibling walk and mutates the live DOM (`toRemove.forEach(el => el.remove())`) during render.
- **Impact:** any future nesting change under Recommended (e.g. wrapping in a section container) silently breaks extraction or removes the wrong nodes; overlaps the exact fragility class Concern 3 calls out.
- **Fix direction:** after section-wrap runs, query within the recommended section container (or reuse `_collectUntil`) instead of a raw H2 sibling walk; avoid dual ownership of “section boundary” logic.

#### [MINOR] Several exported symbols are never imported by any other module

- **Concern:** design-patterns
- **Files:** (sample; cross-checked against `window.*` assignments in `js/app.js` and `onclick=` names in `index.html`) `js/api.js: BACKEND_URL`; `js/app/mobile-panels.js: isMobileTocOpen, openMobileToc, closeMobileToc, closeTopPanel`; `js/auth.js: validatePassword, PW_RULES`; `js/content/code-blocks.js: buildSourceHeader`; `js/content/tables.js: isComplexityTable`; `js/content/zoom-lightbox.js: openZoomOverlay`; `js/modal-registry.js: closeTopModal`; `js/render/changelog-view.js: parseChangelog`; `js/render/content-view.js: closePeekSheet`; `js/render/home-gestures.js: refreshIndex`; `js/render/home-index.js: getPinnedWikis, renderIndexSections, renderIndexControls, attachIndexCardKeyNav, attachIndexCardHoverPreview, populateIndexReadTimes`; `js/render/router.js: resolveSlugAndRender, nearestSlugMatch`; `js/search.js: isGlobalSearchOpen`; `js/state.js: FADE_FLOOR`; `js/storage/bookmarks.js: isBookmarked`; `js/storage/offline.js: downloadArticle, isArticleCached`; `js/storage/read-tracking.js: getReadSet, getRevealCount`; `js/storage/settings-theme.js: saveSettings`
- **Observation:** many of these are same-domain helpers exported “just in case,” or only used inside their defining module. Not all are dead at runtime (some may be reserved for tests or future wiring), but they inflate the public surface.
- **Impact:** readers treat exports as load-bearing API; unused exports also hide which symbols are truly cross-module contracts.
- **Fix direction:** un-export anything only used in-file; for intentional public helpers, add one importing call site or document as test/window API. Re-verify `closeTopModal` / mobile TOC exports against Escape-stack plans before deleting.

### Test quality

#### [MAJOR] `page.evaluate(...click())` still used to interact with auth controls

- **Concern:** test-quality
- **Files:** `tests/e2e/test_auth.py:991`, `:1052`, `:1058`, `:1092`, `:1095`, `:1157`, `:1255`, `:1258`; also `tests/e2e/test_content_enhancements.py:1664` (`window.__copyBtnRef.click()`)
- **Observation:** CONVENTIONS bans `page.evaluate("element.click()")` interactions because they bypass Playwright actionability. Auth suite still double-clicks submit/resend via in-page `.click()`; copy-SVG test drives a stashed button ref the same way.
- **Impact:** tests can pass while the real control is `aria-hidden`, covered, or disabled — exactly the regression class the rule exists to catch. Flag for behavioral follow-up if clicks were added to dodge an actionability failure.
- **Fix direction:** replace with `page.locator(...).click()` (or `expect(...).to_be_enabled()` + click). If production blocks actionability, fix production, don’t bypass in evaluate.

#### [MINOR] One remaining `page.query_selector()` call

- **Concern:** test-quality
- **Files:** `tests/e2e/test_content_enhancements.py:318` (`th = page.query_selector(".sortable-th")`)
- **Observation:** CONVENTIONS prefers `locator` + `expect`; this is a lone holdout in an otherwise large suite.
- **Impact:** inconsistent assertion style; null-check footgun vs auto-retrying locator.
- **Fix direction:** `page.locator(".sortable-th").first` + `expect`.

#### [MINOR] `wait_for_timeout` still widespread (41 call sites)

- **Concern:** test-quality
- **Files:** across `test_auth.py`, `test_behavioral_fixes.py`, `test_bookmarks.py`, `test_content_enhancements.py`, `test_home.py`, `test_index_ux.py`, `test_line_numbers_pathing_help.py`, `test_navigation_polish.py`, `test_notes_scratchpad.py`, `test_read_toggle.py`, `test_routing_pathing.py`, `test_scroll_toc.py`, `test_search.py`, `test_settings.py`, `test_touch_gestures.py`, `test_ux_hotkeys_errors.py` (41 total)
- **Observation:** several are clearly sanctioned (debounce waits in `test_notes_scratchpad.py`, negative-assertion timing in `test_bookmarks.py:101`, placeholder rotation in `test_search.py:433`). Many others are bare `wait_for_timeout(100|200|300)` beside UI transitions with no comment tying them to a fixed timer or negative assertion.
- **Impact:** flake under load; teaches “sleep until green” over waiting on a locator/condition.
- **Fix direction:** for each non-commented sleep, either add the sanctioned rationale comment or replace with `expect` / `wait_for_function` on the real completion signal.

#### [POLISH] Multi-line section-banner comments are the dominant JS comment style

- **Concern:** documented-rule-violation
- **Files:** widespread `/* ═══ ... ═══ */` banners across `js/app.js`, `js/auth.js`, `js/content/*.js`, `js/modal-registry.js`, etc. (75 `/* */` blocks spanning 3+ lines in `js/`)
- **Observation:** CONVENTIONS says comments should be one line or none. The repo’s established section-banner style conflicts with that written rule; most banners are navigational, not prose restatements.
- **Impact:** rule-vs-practice drift makes mechanical enforcement noisy; not a runtime issue.
- **Fix direction:** either amend CONVENTIONS to allow one-line-or-banner section markers, or stop adding new multi-line banners and prefer `// ── Section ──` one-liners going forward. Do not mass-delete banners in a cleanup drive without a docs decision.
