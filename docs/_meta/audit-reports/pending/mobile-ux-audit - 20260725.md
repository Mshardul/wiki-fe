Generated by mobile UX audit agent. Viewports tested: 360px, 375px, 393px, 768px (+ landscape variants of 375px/393px for orientation-change checks).

## Testing limitation

**Live browser verification was not possible in this session.** The Playwright MCP server (`npx @playwright/mcp@latest`, launched from the marketplace-owned `.mcp.json` with no `--browser` flag) defaults to the `chrome` channel and requires system Google Chrome at `/Applications/Google Chrome.app`, which is not installed in this environment (only the Playwright-bundled Chromium under `~/Library/Caches/ms-playwright/chromium-1232` exists). Every `browser_navigate` call failed with `Chromium distribution 'chrome' is not found`. This is the same known MCP-config issue flagged in `CLAUDE.md` ("don't run `npx playwright install chrome`; the browser already exists, it's an MCP server config issue") — not fixable by reinstalling, and not fixable by me without editing marketplace-owned MCP config, which is out of scope for an audit task.

**Consequence:** this pass is Phase-1 (static code read-through) only, for the entire checklist, not just the touch-emulation nuance the task anticipated. Every finding below is a code-level hypothesis, not a live-confirmed bug — severities are assigned on the same bar as if verified (i.e. "this WILL happen" language is used where the code logic is unambiguous), but nothing here carries a screenshot or a live `getBoundingClientRect()`/`getComputedStyle()` measurement. A human (or a future session with a working browser channel) should spot-check the CRITICAL and MAJOR items live before treating them as confirmed, especially anything gesture/touch-event related (swipe, pinch, drag) since those literally cannot be exercised via static reading.

A user-scoped Playwright MCP override (`--browser=chromium`) was registered mid-session to fix this for future sessions, but browser tool bindings are session-scoped — a retry within this same session still hit the identical error, so this pass stayed static-only throughout. A fresh session started after the override should be able to complete live verification.

### Topbar/nav

#### [MAJOR] Content-view topbar icon buttons pinned to 34x34px at exactly 360px/375px — a higher-specificity rule silently defeats the 44px `(pointer:coarse)` fix
- **Page/component:** Topbar/nav — content view topbar icon buttons
- **File:** `css/responsive.css:344-349` (`@media (max-width:375px) { .content-topbar .topbar-icon-btn { min-width:34px; min-height:34px } }`) vs. `css/responsive.css:430-433` (`@media (pointer:coarse) { .topbar-icon-btn { min-width:44px; min-height:44px } }`), base rule `css/components/topbar.css:259`
- **Viewport(s):** 360px, 375px (not 393px or 768px)
- **Repro (code-level, CSS specificity):** `.content-topbar .topbar-icon-btn` (two class selectors, specificity 0-2-0) sets the icon buttons to a deliberately-shrunk 34x34px at `max-width:375px`, per the comment above it ("topbar row overflows 390px viewports... shed read-time badge and back-btn label"). The `(pointer:coarse)` block bumps plain `.topbar-icon-btn` (one class selector, specificity 0-1-0) back up to 44x44px — but lower specificity always loses to higher specificity regardless of source order or media-query nesting. On any touch device at 360-375px width (both in this audit's test matrix: "Small Android" 360px and "iPhone SE/mini" 375px), the computed size stays 34x34px — the touch-target fix silently never applies for the two smallest phone classes tested. It works correctly at 393px (the 375px breakpoint's higher-specificity rule stops applying there) and at 768px (topbar collapses into the overflow menu before this matters).
- **Impact:** On the two smallest, most common small-phone breakpoints, every content-view topbar icon (bookmark, read-toggle, focus, offline, print, quiz, search, settings, overflow-menu trigger) is a 34px touch target — about 58% of the recommended minimum tap area, at exactly the screen sizes where precision is hardest.
- **Fix direction:** Either raise the `(pointer:coarse)` rule's specificity to match/exceed `.content-topbar .topbar-icon-btn` (e.g. qualify it the same way, or strip the size-shrinking rule's specificity with `:where()`), or fold the touch-target minimum directly into the `max-width:375px` block so the two rules never fight — keep the visual/icon area compact but pad the hit-slop to 44px via padding rather than `min-width`/`min-height`.
- **Status:** this is a pure CSS-cascade deduction (specificity math), not a rendered-pixel measurement — high confidence but flagged for a live pixel-check to be certain no other rule intervenes.

### Text zoom / OS font-scaling (cross-cutting)

#### [MAJOR] App's own "S" font-size setting (14px root) drops several text inputs under the 16px iOS auto-zoom threshold
- **Page/component:** Cross-cutting — Auth modal, Global search modal, TOC notes scratchpad, in-article find bar
- **File:** `index.html:44-48` (`sizes = {S:"14px", M:"16px", L:"18px"}`, sets `document.documentElement.style.fontSize` directly, not a scale multiplier), `css/tokens.css:52-54` (`--text-xs:0.72rem`, `--text-sm:0.85rem`, `--text-base:1rem`), `css/components-auth.css:63-70` (`.auth-field input{font:inherit}`), `css/components/search-modal.css:51-57` (`.gsearch-input{font-size:var(--text-base)}`), `css/view-content/layout.css:214-230` (`.notes-scratchpad-input`, uses `--text-xs`), `css/view-content/interactive.css:222-230` (`.article-find-input`, uses `--text-sm`)
- **Repro (code-level):** The app's font-size preference sets the root `<html>` element's `font-size` directly in px, so every `rem`-based value scales with it. At the "S" setting, `1rem = 14px`: `.auth-field input` (`font:inherit` → `--text-base` → 14px) and `.gsearch-input` (`font-size:var(--text-base)` → 14px) both drop under the 16px iOS auto-zoom threshold. `.notes-scratchpad-input` (`--text-xs` = 0.72rem) and `.article-find-input` (`--text-sm` = 0.85rem) are under 16px **at every font-size setting including "L"** (0.72×18=13px, 0.85×18=15.3px) — those two are broken regardless of the user's preference, not just at "S". All measurements are arithmetic from source values, not live-measured.
- **Impact:** iOS Safari auto-zooms the viewport when a focused input's computed font-size is under 16px. A user who has chosen the app's own "S" reading-size preference — an ordinary, encouraged customization, not an edge case — gets unwanted page zoom focusing the login email field or the global search box. Two other inputs (notes scratchpad, in-article find) trigger the same zoom for every user regardless of font-size preference. The zoom then has to be manually pinched back out and can leave the layout visibly offset.
- **Fix direction:** Pin form-control font-size to an absolute floor of 16px (e.g. `max(16px, var(--text-base))` or a dedicated `--text-input-min` token) on all text inputs/textareas/selects, independent of the user's scalable root font-size and independent of which semantic size token a given input happens to use. This is one fix applied consistently, not four separate ones.
- **Status:** needs live verification (iOS Safari-specific zoom behavior; not reproducible in desktop Chromium even if the browser channel worked, and not the kind of thing static analysis can be 100% certain about without a real WebKit engine).

### Momentum scroll / rubber-banding vs modals (cross-cutting)

#### [MAJOR] No scroll-lock on `<body>` for search, preferences, or auth modals — only the TOC drawer locks scroll, and only under 900px
- **Page/component:** Global search modal, Preferences modal, Auth modal (cross-cutting)
- **File:** `js/search.js:536-604` (`openGlobalSearch`/`closeGlobalSearch`), `js/storage/settings-theme.js:354-410` (`Settings.open`/`close`), `js/auth.js:100-116` (`AuthModal.open`/`close`), `css/responsive.css:237-241` (only `body.toc-open{overflow:hidden}` exists, scoped to `@media (max-width:900px)`)
- **Repro (code-level):** Grepped every modal-open/close path in the app for a body scroll-lock mechanism. Only one exists: `mobile-panels.js:33` adds `body.classList.add("toc-open")`, and `responsive.css:238` turns that into `overflow:hidden` — but only inside `max-width:900px`. `openGlobalSearch`, `closeGlobalSearch`, `Settings.open`, `Settings.close`, `AuthModal.open`, `AuthModal.close` never touch `document.body.classList` or `document.body.style.overflow`, at any viewport width.
- **Impact:** On iOS Safari (and to a lesser extent Android Chrome), background content behind a `position:fixed; inset:0` modal can still rubber-band/scroll via touch-drag, since nothing prevents the underlying page from moving. This can produce a visible content shift behind the modal, or the page "jumping" to a different scroll position once the modal closes — a well-known iOS Safari fixed-position/scroll interaction quirk. Exposure isn't uniform: `.prefs-panel` and `.auth-dialog` (mobile width) both already have `overscroll-behavior: contain`, which mitigates (though doesn't fully replace) the missing body-level lock. `.gsearch-results` has `-webkit-overflow-scrolling:touch` but **not** `overscroll-behavior:contain` — it's the most exposed of the three (see Global search modal section for the isolated fix).
- **Fix direction:** Add a shared `body.modal-open { overflow: hidden }` (or a scroll-lock utility storing/restoring `scrollY` via `position:fixed` on body, the more robust iOS-safe pattern) and toggle it from all four modal open/close paths (search, preferences, auth, TOC — unify with the existing TOC one rather than keeping it viewport-gated differently).
- **Status:** needs live verification — iOS Safari rubber-band specifically cannot be confirmed via static read or via Playwright/Chromium even when the browser channel works, since this is a WebKit-specific scroll-chaining behavior.
