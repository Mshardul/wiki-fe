## Findings by concern

### XSS via unsanitized markdown output

#### [MAJOR] Preview render fails open when DOMPurify is undefined

- **Concern:** xss-sanitization
- **Files:** `js/render/content-view.js:821`
- **Observation:** `previewEl.innerHTML = typeof DOMPurify !== "undefined" ? DOMPurify.sanitize(rawHtml) : rawHtml;` - falls back to unsanitized `rawHtml` (markdown-derived HTML) when `DOMPurify` is undefined, same fail-open shape flagged in the prior audit round.
- **Impact:** if the DOMPurify CDN script fails to load (network failure, ad-blocker, CDN outage), the hover-preview render path injects raw markdown-derived HTML unsanitized, reopening XSS via any malicious content reaching this path.
- **Fix direction:** fail closed - skip the render or escape via `escHtml` instead of rendering raw HTML when DOMPurify is unavailable.

#### [MAJOR] Main content render also fails open when DOMPurify is undefined

- **Concern:** xss-sanitization
- **Files:** `js/render/content-view.js:328-335`
- **Observation:** `body.innerHTML = typeof DOMPurify !== "undefined" ? DOMPurify.sanitize(rawHtml, {...}) : rawHtml;` - the primary article-content render path shares the identical fail-open conditional-sanitize shape as the preview path above.
- **Impact:** same precondition as the preview finding (DOMPurify CDN unavailable) but on the main article body - the highest-traffic render path in the app - reopens XSS on every page view during a CDN outage/ad-block, not just on hover-preview.
- **Fix direction:** fail closed - skip the render or escape via `escHtml` instead of rendering raw HTML when DOMPurify is unavailable. Since this is the shared shape behind both findings, a single helper (e.g. `sanitizeOrFail(html)`) used at both call sites would prevent regression.

### localStorage trust boundaries

#### [MAJOR] Backup import validates value *type*, not value *content*, before writing to localStorage

- **Concern:** localstorage-trust
- **Files:** `js/storage/settings-theme.js:353-357` (`BACKUP_SCHEMA`), `:369-379` (`_validateBackup`), `:811-818` (import write)
- **Observation:** `BACKUP_SCHEMA` checks `bookmarks`/`recents`/`settings` with `(v) => v === null || typeof v === "string"` only - it confirms the field is *a string*, not that it's well-formed JSON matching the shape each consumer expects (`getBookmarks()`/`getRecents()` do `JSON.parse(...)` on read with a `try/catch` that silently falls back to `[]`, but `getSettings()` also falls back to defaults on parse failure - so malformed JSON degrades gracefully, but the schema check gives no assurance the *parsed* value is a well-formed array/object at all, only that the raw string type is correct). A user importing a backup file from an untrusted source (per the prompt's own threat model) can supply any string content, including deeply nested or malformed structures, and it is written directly into live localStorage without deeper validation.
- **Impact:** an attacker-crafted backup JSON (e.g. shared as a "restore my progress" file) writes an arbitrary string blob into `wiki-bookmarks`/`wiki-recents`/`wiki-settings` with only a `typeof` gate. Downstream render paths (`bookmarks.js`, `recents.js`) do escape on output via `escHtml`, so direct script-injection via bookmark/recent titles is not currently exploitable through this path - but the validation gap means the "shape-checked, not content-validated" pattern the prompt flagged is real: the schema function name (`_validateBackup`) implies stronger guarantees than it provides.
- **Fix direction:** after the `typeof` check, `JSON.parse` each field and validate its *parsed* shape (e.g. `bookmarks` must parse to an array of objects with expected string keys) before accepting it, matching the stronger pattern already used for `wiki-completed-*` keys via `_isValidCompletionsValue` (which does parse-and-shape-check, not just `typeof`).
