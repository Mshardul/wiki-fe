### zoom-lightbox.js

#### [MINOR] Pinch-release swipe-dismiss guard doesn't cover asymmetric finger-lift
- **Type:** isolation
- **Component(s):** `js/content/zoom-lightbox.js`
- **Parameter:** isolation correctness
- **File:** `js/content/zoom-lightbox.js` (bindZoomGestures touchend handler, `pinchOccurred` flag)
- **Repro:** Pinch-zoom with two fingers, then lift one finger before the other (common in real pinch gestures — fingers rarely lift simultaneously). `pinchOccurred` is only reset to `false` when `e.touches.length === 0` at the very end of the handler; after the first finger lifts, `e.touches.length` is still 1, so a subsequent code path could see `singleTouchStart`/`panning` state left over from before the pinch, since `touchstart`'s 2-touch branch clears `startX`/`startY` but the 1-touch state machine (`singleTouchStart`, `panning`) isn't fully re-synchronized until a fresh single-touch `touchstart` fires.
- **Impact:** A plausible but not confirmed path to an accidental swipe-dismiss immediately after a pinch-zoom, if the final single-finger lift's coordinates happen to satisfy the `dy > 80` swipe threshold relative to stale `startY`. Not live-verified (requires precise multi-touch event sequencing outside this pass's time budget) — logged as a code-level hypothesis, not a confirmed repro.
- **Fix direction:** Reset `pinchOccurred` (and re-baseline `startX`/`startY`) on the transition from 2-touch to 1-touch within `touchmove`/`touchend`, not only when `touches.length` reaches 0.

- persistence: N/A, no localStorage/sessionStorage use.
- resource lifecycle: verified safe — `getZoomOverlay()` and `bindZoomGestures()` both run inside a `document.getElementById` singleton guard, so the overlay element and its touch/click listeners are created exactly once per page load regardless of how many times zoom is opened/closed or how many articles are navigated. `addImageLightbox`/`addDiagramZoom`/`wireImageErrorPlaceholders` attach fresh per-render listeners only to `#markdown-body`-scoped elements that are wiped on navigation — no accumulation.
- failure-path: an `<img>` that 404s is replaced via `wireImageErrorPlaceholders`'s `{ once: true }` error listener before any zoom-click listener could fire on it again — placeholder correctly has no zoom affordance since the original image node (carrying the click listener) is removed from the DOM.

### tables.js

- **Type:** isolation
- **Component(s):** `js/content/tables.js`

### toc.js

#### [MAJOR] Empty-id heading breaks collapse-state sync between TOC chevron and content heading
- **Type:** isolation
- **Component(s):** `js/content/toc.js`
- **Parameter:** edge-case input
- **File:** `js/content/toc.js:43` (buildTOC collapseKey), `js/content/toc.js:168` (injectHeadingCollapseToggles key), `js/content/toc.js:293-297` (_syncContentH2)
- **Repro:** An h2 with no `id` attribute (markdown heading text that produces an empty/falsy slug, or an anchor-link step that fails to assign one). `injectHeadingCollapseToggles` sets `h2.dataset.sectionId` to a random fallback (`h2-<random>`) only when `h2.id` is falsy, but the localStorage `key` on line 168 and `buildTOC`'s `collapseKey` on line 43 both use raw `h.id` directly, not the fallback. `_syncContentH2` (called from the TOC chevron's click handler via `h.id`) looks up `h2[data-section-id="${h2Id}"]` — but `dataset.sectionId` was set to the random fallback, not empty string, so the lookup selector never matches.
- **Impact:** For any heading missing an id, clicking the TOC chevron does not sync the corresponding content-heading collapse state (and vice versa via `_syncTocGroup` which does use the correct `sectionId`, creating an asymmetric break — one direction works, the other doesn't). Multiple id-less h2s in the same article would also collide on the same localStorage key, corrupting each other's persisted collapse state.
- **Fix direction:** Use the same fallback-safe identifier consistently in `buildTOC`'s collapseKey, `injectHeadingCollapseToggles`'s key, and `_syncContentH2`'s lookup — either guarantee every h2 always has a stable id upstream (anchor-link generation step), or thread `dataset.sectionId` through all three instead of raw `h.id`.

### highlights.js (content)

#### [CRITICAL] Marker-badge insertion during applyHighlightsAndMarkers corrupts subsequent marker/highlight offsets in the same load
- **Type:** isolation
- **Component(s):** `js/content/highlights.js`
- **Parameter:** isolation correctness
- **File:** `js/content/highlights.js` (applyHighlightsAndMarkers, `_insertMarkerBadge`, `_textNodes`)
- **Repro:** An article with two or more saved emoji markers (`storage/highlights.js` `Markers`) at different offsets in the same article. `applyHighlightsAndMarkers` computes `fullText = contentEl.textContent` once, then processes markers sorted ascending by offset, calling `_nodeAtOffset`/`_insertMarkerBadge` for each — but `_insertMarkerBadge` sets `badge.textContent = entry.emoji`, which inserts 1-2 new UTF-16 code units of real text into the live DOM. `_textNodes`'s `TreeWalker` does not exclude `.wiki-marker` spans, so every marker/highlight processed after the first now has its offset computed by `_nodeAtOffset` walking a DOM whose earlier offsets are already shifted right by the cumulative length of previously-inserted badge emoji — but the offsets themselves come from the original pre-insertion `fullText` snapshot, never adjusted for badges inserted so far. **Live-verified** via Playwright: reimplemented the exact `_textNodes`/`_nodeAtOffset`/`_insertMarkerBadge` mechanics against `"The quick brown fox jumps over the lazy dog"` with two markers at offsets 4 ("q" of quick) and 16 ("f" of fox). After inserting the first 2-code-unit emoji badge (🤔), the second marker's `_nodeAtOffset` lookup at offset 16 resolved to `"n"` (inside "brown") instead of the expected `"f"` — confirmed off by exactly the first badge's code-unit length. Final DOM: `The <span class="wiki-marker">🤔</span>quick brow<span class="wiki-marker">⭐</span>n fox jumps over the lazy dog`.
- **Impact:** Any article with 2+ saved markers (or a marker followed by a highlight) will have all but the first marker/highlight land at a position offset by the cumulative code-unit length of earlier badges in the same load — visibly wrong placement (marker landing 1-2 characters off, worse with more markers), potentially compounding further as errors stack. Stored localStorage offsets are not corrupted — this is a live-DOM placement bug on every render after the first marker, not a data-integrity bug in the persisted entries themselves.
- **Fix direction:** Track a running "inserted-length" offset adjustment as each marker badge is inserted (add `badge.textContent.length` to a cumulative delta and add it to all subsequent offsets before calling `_nodeAtOffset`), or perform all `_nodeAtOffset` lookups against the original `fullText` coordinate space before any DOM mutation occurs (resolve all ranges first, then insert badges back-to-front so earlier insertions don't shift not-yet-processed offsets — inserting in descending offset order would sidestep the whole issue).

### settings-theme.js

#### [MAJOR] _saveSettings / importData never guard localStorage.setItem exceptions
- **Type:** isolation
- **Component(s):** `js/storage/settings-theme.js`
- **Parameter:** failure-path
- **File:** `js/storage/settings-theme.js:265-267`, `js/storage/settings-theme.js:786-793`
- **Repro:** `_saveSettings(s)` is a bare `localStorage.setItem(SETTINGS_KEY, JSON.stringify(s))` with no try/catch. Every `Settings._set*` handler (`_setBackground`, `_setFont`, `_setSize`, etc.) calls it synchronously from an inline `onclick`. In Safari private browsing (throws on any localStorage write) or once storage quota is exceeded, this throws uncaught, aborting the handler - all current setters call `_saveSettings` before `applySettingsToDOM`, so a throw here means the DOM update for that click never happens at all, and the click silently does nothing from the user's perspective.
- **Impact:** In Safari private mode / quota-exceeded environments, every settings control (background, accent, font, size, width, line-height, paragraph spacing, toggles) becomes dead-silent - clicking has zero visible effect and no error is surfaced, directly violating CONVENTIONS.md's "fail loud in dev" / user-visible-errors principle.
- **Fix direction:** wrap `_saveSettings` in try/catch, still call `applySettingsToDOM` for the in-session visual change even if persistence fails, and surface a toast on persistent failure so the user knows the choice won't survive reload.

#### [MINOR] getSettings() swallows corrupt localStorage JSON with no signal
- **Type:** isolation
- **Component(s):** `js/storage/settings-theme.js`
- **Parameter:** failure-path
- **File:** `js/storage/settings-theme.js:248-263`
- **Repro:** `getSettings()` catches any `JSON.parse` failure and silently falls through to OS-preference defaults. A corrupted `wiki-settings` key (partial write from a crash, manual edit, or the quota-exceeded case above) is indistinguishable from "never configured" - the user's actual preferences are lost with no toast/warning, and the corrupt value stays in localStorage untouched (next call reparses it and fails again every time `getSettings()` runs, which is on every render).
- **Impact:** Silent, permanent loss of saved preferences with no indication to the user that anything went wrong; the corrupt key is also never cleaned up.
- **Fix direction:** on parse failure, clear the corrupt key (or repair it) and optionally toast once that preferences reset.
