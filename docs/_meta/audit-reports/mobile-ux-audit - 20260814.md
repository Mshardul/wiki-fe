# Mobile UX Audit

Generated by mobile UX audit agent. Viewports tested: 360px, 375px, 393px, 768px (+ landscape
variants of 375px/393px for orientation-change checks, and 768x1024 / 1024x768 for tablet rotation).

Live Playwright browser verification is available this session, with CSS-level mobile emulation forced
via CDP (`context.newCDPSession(page)` → `Emulation.setTouchEmulationEnabled({enabled:true,
maxTouchPoints:5})` + `Emulation.setEmitTouchEventsForMouse({enabled:true, configuration:'mobile'})`)
since the MCP's own `browser_resize` does not set `pointer:coarse`/`hover:none`/`navigator.maxTouchPoints`
by default — a plain resized viewport still reports `pointer:fine`/`hover:hover`, which would have
silently invalidated every `(pointer:coarse)` CSS check in this audit. After the CDP call,
`matchMedia('(pointer:coarse)')` and `(hover:none)` correctly flip. Residual limitation: `'ontouchstart'
in window` still reports `false`, and `browser_click`/`browser_type` still dispatch mouse events, not
real `TouchEvent`s — so JS gesture code paths that branch on `e.touches`/`touchstart` (swipe, pinch,
pull-to-refresh) could not be exercised end-to-end via standard click/drag tool calls; those are marked
as code-read findings below rather than live-verified. Live verification was otherwise used selectively:
for actual rendered overflow/clipping, interactive behavior (drawer open/close, gesture handlers, modal
focus), and anything ambiguous from static reading alone. Clear-cut findings fully provable from CSS/JS
alone (fixed px with no matching media query, hover-only handlers with no touch fallback, definite
sub-44px dimensions from computed CSS values) are logged directly as code-read findings without a live
round-trip, noted as "not live-verified."

### Content view — mermaid diagrams

#### [CRITICAL] Diagram zoom overlay renders a blank/empty box — the "blank zoom overlay" bug is NOT actually fixed, contrary to the 20260725 static-only audit's conclusion
- **Page/component:** Content view — mermaid diagram zoom (shared `.zoom-overlay` with image lightbox)
- **File:** `js/content/zoom-lightbox.js:239-247` (`addDiagramZoom`, `svgEl.cloneNode(true)`), `css/view-content/mermaid.css:248-296` (`.zoom-overlay-content`, `.zoom-diagram-svg`)
- **Viewport(s):** 360px, live-confirmed with touch emulation; root cause is layout-engine-level (flex sizing), not viewport-specific, so almost certainly reproduces at all four matrix widths
- **Repro:** Open any article with a mermaid diagram (e.g. `dsa/data-structures/heap.md`) → tap/click the diagram → zoom overlay opens (`display:flex`, visible) but is functionally blank — only the close button and dimmed backdrop are visible, no diagram content renders
- **Root cause (confirmed via `getComputedStyle`):** the live in-article SVG that mermaid.js renders has an SVG **attribute** `width="100%"` (set at runtime by mermaid's own render step, not present in any CSS — this is why the 20260725 static-only code-read audit missed it, it only checked CSS). `addDiagramZoom` clones this SVG with `cloneNode(true)`, carrying the `width="100%"` attribute into the zoom overlay. The overlay's `.zoom-overlay-content` is `display:flex; align-items:center; justify-content:center` with no explicit width — it sizes to its child's content. The cloned SVG's `width="100%"` needs a sized parent to resolve against, and the flex parent needs the SVG's intrinsic size to size itself — a circular reference that Chromium resolves to `0px` on both sides. `.zoom-diagram-svg { width:auto; height:auto }` in CSS does not fully override the `width="100%"` SVG presentation attribute in this flex context. Confirmed live: `getComputedStyle(.zoom-diagram-svg).width === "0px"`, `getComputedStyle(.zoom-overlay-content).width === "0px"`.
- **Impact:** every mermaid diagram is unusable in zoomed/fullscreen mode on mobile — the one feature meant to make diagrams legible on a small screen instead shows nothing. User must pinch-zoom the tiny inline diagram instead (if pinch-zoom isn't disabled by `touch-action`) or give up on reading the diagram.
- **Fix direction:** in `addDiagramZoom`, either strip the `width`/`height` attributes from the cloned SVG before appending (`clone.removeAttribute('width'); clone.removeAttribute('height')`) so the CSS `width:auto` rule has nothing competing with it, or give `.zoom-overlay-content` an explicit `width:auto; max-width:92vw` sizing strategy that doesn't depend on shrink-to-fit against a percentage-width child.
- **Method note:** this directly contradicts the 20260725 audit's `[CONFIRMED-BY-CODE]` entry claiming this bug was fixed — that pass had no working browser and only read the CSS, missing the runtime-set `width="100%"` attribute mermaid.js adds to the live SVG. This is the clearest example in this session of why live verification catches what static reads cannot.

### Text zoom / OS font-scaling (cross-cutting)

#### [MAJOR] Breadcrumb becomes functionally unreadable at 200% text zoom — truncates to 2-3 characters
- **Page/component:** Content view — topbar breadcrumb
- **File:** `css/components/topbar.css:9-14` (`.breadcrumb-link`, `text-overflow:ellipsis`), `css/responsive.css:124-135` (mobile truncation rules, `min-width:2.5em`/`3.5em`)

### Momentum scroll / rubber-banding vs modals (cross-cutting)

#### [MAJOR] No shared body scroll-lock mechanism exists — only the mobile TOC drawer locks the body; every other modal relies solely on `overscroll-behavior: contain` (or nothing)
- **File:** `js/modal-registry.js` (shared focus-trap + open-state tracking for all modals — confirmed via full read, contains zero `document.body.style` or scroll-lock logic of any kind), `css/responsive.css:218-221` (`body.toc-open { overflow: hidden }`, gated to `max-width:900px` — the only body-level scroll-lock rule in the entire codebase, confirmed via grep for `overflow:\s*hidden` scoped to `body`)
- **Not live-verified** — code-confirmed from the complete absence of any scroll-lock call site outside the one CSS rule found
- **Repro (code-level):** open the global search modal, preferences modal, auth modal, or wiki-switcher modal on a real iOS Safari device, then attempt to scroll starting with a touch that lands on the modal's backdrop (not its internal scrollable content) — the background page underneath is free to scroll/rubber-band since nothing sets `overflow:hidden` on `body` for any of these four
- **Partial mitigation already present:** `.gsearch-dialog`/`.gsearch-results` (search-modal.css:97), `.prefs-panel` (preferences-modal.css:293), `.auth-dialog`/`.migrate-dialog` (auth.css:298,315) all set `overscroll-behavior: contain` on their own internal scroll containers — this stops scroll-chaining once a touch-scroll gesture is already inside the modal's content and hits its top/bottom boundary, which covers the most common case (user scrolls modal content, hits the end, chain-scrolls the page behind it). It does **not** cover a touch that starts on the backdrop itself, and it's entirely absent for `.wiki-switcher-list` and the bookmarks-modal (`css/components/wiki-switcher.css`, `css/components/bookmarks-modal.css` — confirmed zero `overscroll-behavior` matches in either file).
- **Impact:** on iOS Safari specifically, background content can visibly shift/rubber-band while a modal is open, or the page can be left at a different scroll position after the modal closes than where it was before — the exact symptom the audit brief describes. Wiki-switcher and bookmarks-modal have no protection at all (not even the partial `overscroll-behavior` mitigation); search/preferences/auth have the partial mitigation but not a full lock.
- **Fix direction:** add a shared `lockBodyScroll()`/`unlockBodyScroll()` pair to `modal-registry.js` (e.g. toggling a `body.modal-open { overflow:hidden }` class, matching the existing `.toc-open` pattern) and call it from each modal's open/close, or generalize `body.toc-open` into a shared class all modal controllers add/remove. The existing `overscroll-behavior:contain` rules stay useful as defense-in-depth even after a proper lock is added.
